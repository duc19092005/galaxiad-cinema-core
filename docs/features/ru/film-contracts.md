# Договоры на фильмы и права показа

Модуль заменяет прямой CRUD фильмов проверяемым процессом:

`Загрузка Admin → немедленный OCR/анализ моделью → (опционально) назначение MovieManager → сравнение до/после → внутренняя подпись Admin → активация → связь фильма, права показа и политика распределения выручки.`

## Роли и жизненный цикл

- **Admin** загружает досье, проверяет OCR, фильтрует по партнёру, при необходимости назначает активного MovieManager, публикует шаблоны, одобряет, подписывает, активирует, приостанавливает/завершает договоры и одобряет изменения метаданных. Для Admin больше нет ошибочного действия «отправить Admin»: при необходимости можно сразу перейти к подписанию.
- **MovieManager** работает только с назначенными досье: загружает файлы, повторяет OCR, исправляет черновик извлечения, отправляет на проверку и предлагает изменение метаданных. Роль не может напрямую создавать, изменять, удалять или включать фильм.
- **TheaterManager** формирует расписание только по активированным правам показа с учётом кинотеатра, формата и периода.

Статусы: `DRAFT`, `PENDING_REVIEW`, `READY_TO_SIGN`, `SIGNED`, `ACTIVATED`, `SUSPENDED`, `TERMINATED`, `CANCELLED`. После загрузки PDF/PNG/JPEG исходный файл сохраняется неизменяемым и запускается OCR. Список проверяющих доступен через `GET /api/contracts/reviewers`, назначение — через `POST /api/contracts/{id}/assign`; MovieManager видит только назначенные досье.

MovieManager изменяет черновик через `PUT /api/contracts/{id}/extraction-review`. Каждое сохранение записывает пользователя, время и JSON до/после в revision; UI показывает сравнение исходного OCR и исправленных значений. После `/submit` Admin проверяет данные, подтверждает пароль, сохраняет внутреннее одобрение и активирует договор. Это запись внутреннего одобрения, а не утверждение о сертифицированной цифровой подписи.

Область кинотеатров/форматов принимает `SPECIFIED`, `NO_ADDITIONAL_RESTRICTION_CONFIRMED` или `UNRESOLVED`. Пустое поле не означает неограниченный показ или долю 50/50.

## API, OCR, хранение и локальная модель

`GET /api/movieManager/movies` остаётся endpoint только для чтения. Старые операции записи возвращают `410 MOVIE_DIRECT_MUTATION_DISABLED` и не меняют БД, файлы или jobs.

Основные API: `/api/contracts`, `/api/contract-templates`, `/api/movies/{id}/change-requests`. Только Admin может одобрить, подписать, активировать или применить изменение. Активация транзакционная и идемпотентна для revision.

### Как работает OCR

1. Admin выбирает PDF, PNG или JPEG. Backend проверяет расширение, сигнатуру, размер (25 MB на файл, 50 MB на job) и число страниц (до 50), затем сохраняет неизменяемый оригинал в MinIO в local/test или production storage. SHA-256 фиксирует источник.
2. Создаётся фоновая job с `contractId` и `revisionId`; интерфейс не блокируется, а старая job не может перезаписать новую revision.
3. Python читает PDF постранично через `pdfplumber`. Если пригодного text layer нет, страница рендерится через `pypdfium2`, переводится в grayscale с усилением контраста и проходит Tesseract `vie+eng`. Изображения используют тот же OCR path.
4. Text сохраняется по страницам со способом (`pdf_text`/`ocr`), предупреждениями и источником. Проверяющий открывает точную страницу, а не одну склеенную строку.
5. Text с номерами страниц отправляется локальной Ollama `qwen3.5:4b` в dev/test. Модель предлагает JSON: правообладатель/партнёр, номер договора, фильмы, описание, poster URL, режиссёр, актёры, даты, область кинотеатров/форматов, доли, clauses, конфликты и нерешённые поля. Документ — недоверенный текст; инструмента изменения БД у модели нет.
6. Service проверяет schema. Неверный/неполный JSON становится `UNRESOLVED`, пустой ответ не считается успехом. Отсутствующие доли, даты, poster или описание остаются нерешёнными; 50/50, даты по умолчанию и URL из Internet не придумываются.
7. Frontend помещает значения в черновик. Имена кинотеатров/форматов превращаются в ID только после совпадения с catalog; «вся сеть» остаётся областью без отдельного ограничения, а не фиктивным кинотеатром. Ошибочные даты и неизвестные названия остаются на проверку.
8. Admin проверяет сам или назначает MovieManager. Каждое сохранение записывает пользователя, время и JSON до/после; UI показывает OCR рядом с исправленным значением и источником.
9. Только подтверждённые обязательные поля и financial policy допускаются к отправке/одобрению. OCR не создаёт фильм; фильм, права и policy создаются после подписи revision Admin и активации.
10. Временные ошибки повторяются job; неверный файл, нечитаемая страница или invalid JSON остаются в dossier с кодом ошибки и не создают дубликаты.

OCR/model — это извлечение с доказательствами, а не подпись договора и не автономное юридическое или финансовое решение.

В Development/Testing приватные договоры хранятся в MinIO. В Production используется существующее backend-хранилище. Docker запускает Ollama с `qwen3.5:4b` без API key, с выключенным reasoning и JSON output.

Партнёр при приёме необязателен: он извлекается из раздела правообладателя/дистрибьютора и подтверждается человеком; список Admin можно фильтровать по партнёру. Отсутствующие описание, постер, даты, классификация, область или доли не заполняются выдуманными значениями. `SPECIFIED` применяется только при сопоставлении с каталогом кинотеатров/форматов; «вся сеть» остаётся `NO_ADDITIONAL_RESTRICTION_CONFIRMED`.

PDF в `sample-contracts/` помечены как demo и содержат Unicode, партнёра, описание и URL постера. Описание фильма хранится в `nvarchar(2048)`; старые символы `?` нужно повторно импортировать из оригинала.

## Проверка в Docker

```powershell
docker compose -p galaxiad-contract-test -f infrastructure/docker/compose.test.yml up -d --build mssql redis qdrant minio ollama ollama-init ai-http api
docker compose -p galaxiad-contract-test -f infrastructure/docker/compose.test.yml build test-runner
docker compose -p galaxiad-contract-test -f infrastructure/docker/compose.test.yml run --rm --no-deps test-runner python3 -m pytest -q services/ai/tests/test_contract_docker_integration.py
```

Интеграционный тест не мокает MinIO, OCR, модель или HTTP. Он создаёт изображение договора, выполняет реальный MinIO round trip, OCR/анализ модели и проверяет отказ API без аутентификации.
